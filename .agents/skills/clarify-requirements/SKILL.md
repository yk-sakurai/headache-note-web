# Clarify Requirements: ファイルベースの要件確認スキル

計画・実装フェーズの前段として、要件の不明点を洗い出し、ファイルベースのQ&Aで要件を確定させるワークフロー。

チャットでのやり取りではなく、マークダウンファイルに確認事項を書き出し、ユーザーがそのファイルを編集して回答する形式を取る。これにより回答を考える時間が取れ、履歴が残り、後続の計画フェーズで参照できる。

## ステータス定義

要件確認ファイルの進行状態を管理する。ステータスは以下の4種類。

| ステータス | 意味 | 遷移条件 |
|-----------|------|---------|
| `確認中` | 未回答の確認事項がある。ユーザーの回答待ち | 初回生成時、または回答確認後に追加質問が発生した場合 |
| `要件確定` | すべての確認事項に回答済み、追加質問なし | 全項目回答済み＋追加質問なし |

```
確認中 → (回答→追加質問→確認中を繰り返し) → 要件確定
```

## フロー全体像

```
1回目: /clarify-requirements "要件の説明"
  → コードベース・スキーマを分析
  → 要件確認ファイルを生成（requirements/{feature-name}.md）
  → ユーザーに「ファイルに回答を記入してください」と伝える

2回目以降: /clarify-requirements
  → 要件確認ファイルの回答を読み取り
  → 未回答の確認、追加質問があればファイルを更新
  → すべて解決なら「要件確定」ステータスに更新
```

## 実行手順

### Step 1: 初回実行 — 要件分析と確認ファイル生成

ユーザーから要件の説明を受け取ったら、以下を実行する。

#### 1-1. コンテキスト収集

要件に関連する情報を収集する。関連性に応じて以下を調査する：

- **Firestoreスキーマ** (`docs/firestore-schema.md`): 対象コレクションの構造、フィールド、サブコレクション、セキュリティルール
- **Hiveスキーマ** (`docs/hive-schema.md`): ローカルストレージのスキーマ定義
- **既存の類似実装**: 同様の機能モジュールのパターン（`lib/features/` 配下）
- **ナビゲーション構造**: `AppRoutes` クラス、ボトムナビゲーション（`TopScreen`）
- **Cloud Functions**: `functions/src/` のスケジュール実行・呼び出し可能関数・トリガー

#### 1-2. 確認観点の分析

以下のカテゴリに沿って確認事項を洗い出す。すべてのカテゴリが毎回必要ではなく、要件に応じて取捨選択する。

**スコープ・境界**
- 対象データの範囲（Firestore コレクション、Hive ボックス、関連リソース）
- 操作の範囲（作成/読取/更新/削除のうちどこまで必要か）
- 画面の範囲（入力画面、一覧画面、詳細画面、設定画面等）
- 機能モジュールの範囲（既存モジュールの拡張 or 新規モジュール）

**データモデル**
- Firestore フィールドの型、必須/任意、デフォルト値
- Hive モデルの TypeID、フィールド定義（`@HiveType` / `@HiveField`）
- クエリパターン（インデックス、並び順、フィルタ条件）
- 既存データとの整合性・マイグレーション

**既存パターンとの差異**
- プロジェクトの確立された機能モジュールパターンとの差異
- `constants/` / `data/` / `presentation/` / `services/` / `validators/` の構成
- サブコレクション、特殊なデータ型など

**UI/UX**
- 入力方式（テキスト、ピッカー、スライダー、セレクト等）
- 表示項目、リスト表示、カレンダー表示
- プラットフォーム差異（iOS / Android 固有の考慮事項）

**外部影響**
- Cloud Functions への影響（新規関数、既存関数の変更）
- Firebase セキュリティルールの変更
- サブスクリプション・課金への影響
- 既存データの移行の必要性

**運用ルール**
- 論理削除 vs 物理削除
- バリデーションルール（`validators/` への追加）
- UI 文字列の定数化（`CommonLabels` / 機能固有の `*_labels.dart`）

#### 1-3. 要件確認ファイルの生成

`requirements/{feature-name}.md` にファイルを生成する。ファイル名は要件を端的に表す英語のケバブケース。

ファイルフォーマット:

```markdown
# 要件確認: {要件タイトル}

## ステータス: 確認中

## 概要

{要件の要約。コンテキスト収集で把握した内容をもとに記載}

## 確認事項

### 1. {確認カテゴリ}: {質問タイトル}

- **背景**: {なぜこの確認が必要なのか、現状の情報}
- **質問**: {具体的な質問}
- **選択肢**（該当する場合）:
  - A. {選択肢A}
  - B. {選択肢B}
- **回答**: <!-- ここに回答を記入してください -->

### 2. {次の確認事項}
...

## リスク・課題

### 1. {リスクタイトル}

- **内容**: {リスクの説明}
- **影響度**: 高 / 中 / 低
- **対応方針案**: {スキルが提案する対応方針}
- **回答**: <!-- 対応方針についてのコメント・修正があれば記入してください -->

## 確認履歴

- {日付}: 初回確認事項を作成
```

#### 1-4. ユーザーへの案内

ファイル生成後、以下を伝える：

- 生成したファイルのパス
- 確認事項の概要（件数と主なカテゴリ）
- 「各確認事項の`回答`欄に記入し、完了したら再度 `/clarify-requirements` を実行してください」

### Step 2: 2回目以降 — 回答確認と更新

引数なしで実行された場合、`requirements/` 内の「確認中」ステータスのファイルを探す。複数ある場合はユーザーに選択を促す。

#### 2-1. 回答の読み取りと分析

- 各確認事項の「回答」欄を読み取る
- リスク・課題の「回答」欄を読み取る
- 未回答の項目を特定する（確認事項・リスク課題の両方を対象とする）
- 回答内容から新たに生じる確認事項がないか分析する

#### 2-2. ファイルの更新

- 回答済みの項目はそのまま保持（ユーザーの記入内容は変更しない）
- **既存の確認事項の構造（背景・質問・選択肢・回答）はすべて保持する。特に選択肢（A, B, C …）は回答後も削除しない。ユーザーが「A」等と回答した場合、選択肢がないと意味が分からなくなるため**
- 新たな確認事項があれば「確認事項」セクションに追記する（既存の番号の後に追加）
- 新たなリスク・課題があれば「リスク・課題」セクションに追記する（既存の番号の後に追加）
- リスク・課題の回答を受けて対応方針を調整する場合は、「対応方針案」の下に「**確定方針**: {回答を反映した方針}」を追記する（元の対応方針案は残す）
- 確認履歴に更新日時を追記する
- 「確認事項」と「リスク・課題」の両方ですべての回答が揃い、追加質問もなければステータスを「要件確定」に変更する

#### 2-3. 要件確定時 — 規模見積もりの生成

ステータスを「要件確定」に変更する際、以下の手順で規模見積もりセクションを要件確認ファイルに追記する。

**見積もり手順:**

1. 確定した要件とコードベースを分析し、以下の指標を算出する：
   - **新規ファイル数**: 新たに作成が必要なファイルの数
   - **変更ファイル数**: 既存ファイルで変更が必要なファイルの数
   - **推定コード行数**: 追加・変更されるコードの概算行数（範囲で記載）
   - **複雑度**: 低 / 中 / 高（判断基準は下記）
   - **レビュー重要度**: 低 / 中 / 高（判断基準は下記）

**複雑度の判断基準:**
- **低**: 既存パターンの単純な適用、テンプレート的な作業
- **中**: 既存パターンの応用＋部分的な新規設計（例: 配列編集UI、複合フォーム）
- **高**: 新規アーキテクチャ設計、複数サービス連携、未知の技術要素

**レビュー重要度の判断基準:**
- **低**: 既存パターンの踏襲で、レビューで指摘が出にくい
- **中**: 部分的に新しいロジックがあり、設計判断のレビューが有用
- **高**: セキュリティ・データ整合性に影響、または新規アーキテクチャで入念なレビューが必要

**要件確認ファイルへの追記フォーマット（「リスク・課題」セクションの後、「確認履歴」セクションの前に挿入）:**

```markdown
## 規模見積もり

| 指標 | 値 |
|------|-----|
| 新規ファイル数 | {数値} |
| 変更ファイル数 | {数値} |
| 推定コード行数 | {範囲}行 |
| 複雑度 | {低/中/高}（{判断根拠を簡潔に}） |
| レビュー重要度 | {低/中/高}（{判断根拠を簡潔に}） |
```

#### 2-4. ユーザーへのフィードバック

以下を伝える：

- 確認事項の回答確認結果サマリー
- リスク・課題の回答確認結果サマリー（対応方針の変更があればその説明）
- 新たに追加した確認事項・リスクがあればその説明
- 未回答の項目があればそのリスト（確認事項・リスク課題を区別して表示）
- ステータスが「要件確定」になった場合はその旨と規模見積もりの概要

## 注意事項

- 確認事項は具体的かつ回答しやすい形で書く。漠然とした質問は避ける
- 選択肢を提示できる場合は提示し、ユーザーの負担を減らす
- リスク・課題は実装に実際に影響するものだけを記載する。些細な事項で埋めない
- ユーザーの回答内容は絶対に変更しない。確認事項・リスク課題ともに、選択肢・背景・質問・対応方針案など既存構造も削除・変更しない。追記・補足は別セクションで行う
- 確認履歴の日付は `date '+%Y-%m-%d %H:%M:%S'` で取得する
